1.5.9 — T28.03 numeric error codes

The TS `onError` interface has always declared `code: number` but
the Kotlin `emitErrorEvent` was emitting a string code, so JS
consumers had to coerce with `Number()` on a string that looked
like `"E_NOT_INITIALIZED"`. This commit closes the gap.

Changes
=======

Kotlin (`MpvBridgeModule.kt`)
- New private `codeToNumeric(code: String): Int` helper with
  documented permanent ranges (1xxx initialization, 2xxx
  activity/launch, 4xxx configuration). Returns 0 for
  unknown codes (single-sentinel degradation).
- `emitErrorEvent` payload now emits `code: Int` + `codeName:
  String` (instead of `code: String`). The string moves
  under `codeName` so logging stays grep-friendly;
  programmatic handlers switch on the integer.
- `Promise.reject` paths unchanged (React Native's Promise
  plumbing expects a string identifier for `code`).

TS (`MpvPlayerModule.ts`, `types/player.ts`)
- `onError` interface extends with `codeName?: string`.
- `PlayerState.error` shape extends the same way and the
  bridge event handler forwards `codeName` through.

Stable mapping (do not reuse numbers across versions):
  E_NOT_INITIALIZED     -> 1001
  E_ACTIVITY_NOT_FOUND  -> 2001
  E_SECURITY            -> 2002
  E_OPEN_PLAYER_FAILED  -> 2003
  E_CONFIG_PARSE_FAILED -> 4001

Compatibility
=============
No consumer code change required to USE the new shape —
existing `if (error.code === 1001)` switches start matching.
Existing destructures like `const {code, message} = error`
keep working. The `codeName` field is optional; old consumers
that destructure only `error.code` keep working unchanged.

The consumer's `src/infrastructure/nativeFs/index.ts` shim
(D-033) and the consumer-side B-005/T13.04 wave (see the
SIMBA consumer repo's commit 45e5ee5) are independent of
this lib release.
